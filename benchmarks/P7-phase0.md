# P7 Phase 0 实测报告 — 投机解码 Go/No-Go

> 日期：2026-10-27 12:55–14:30（第 17 发 30B 加载 + 4 次 draft 加载 + 1 次 0.6B 步时分解）
> 栈：target = Qwen3-30B-A3B-Instruct-2507-FP8（sdpa + grouped_mm prefill + bmm_dense decode，TP2/EP2，eager）；draft = Qwen3-0.6B / Qwen3-1.7B（dense，TP2 与 TP1 各测）。
> 判据（启动前冻结，`docs/P7-speculative-decoding-survey.md` §7.3）：**最优 k 下单流加速 ≥1.3× → go**。

## 0. 判决：**NO-GO（0.73×，与门差 44%）**

| 量 | 调研预估 | **实测** | 偏差 |
|---|---:|---:|---|
| c = draft 步时 / target 步时（0.6B） | 0.07–0.12 | **0.384** | **3–5× 高估了 draft 速度** |
| c（1.7B） | 0.20–0.30 | **0.386** | 1.3–1.9× |
| α（0.6B → 30B） | 0.40–0.60 | **0.0056** | **差两个数量级** |
| α（1.7B → 30B） | 0.60–0.80 | **0.0068** | 同上 |
| 最优加速（k=1） | 1.35–1.55× | **0.725× / 0.741×** | **比基线还慢 26–28%** |

**结论：朴素 draft-model 路线在本项目上不成立。** 两个独立的失败原因（任一个都足以否决）：

1. **draft 太慢（c≈0.39）**——不是因为模型大，而是因为引擎的每步固定成本（§2）。
2. **接受率几乎为零（α≈0.006）**——0.6B/1.7B 与 30B-2507 在 0–4 个 token 内就分叉（32 条 prompt 的 LCP 分布：0.6B `[2,0,3,0,0,1,0,2,0,0,4,...]`，均值 0.72、最大 4）。

## 1. α 实测（32 条真实 chat prompt × 128 greedy tokens）

| draft | α（逐 token 一致率） | LCP 均值 | LCP 最大 | 完全一致的 prompt |
|---|---:|---:|---:|---:|
| Qwen3-0.6B | **0.0056** | 0.72 | 4 | 0/32 |
| Qwen3-1.7B | **0.0068** | 0.88 | 7 | 0/32 |

- 参考轨迹：30B 采用栈贪心（`/root/p7_target_ref.json`，32 prompt × 128 token）。
- **tokenizer 完全一致已排除**：三个模型的 tokenizer 对同一 prompt 逐 token 相同（长度 14/14/14），引擎收到的是 raw encode（无 chat template 差异）。
- **草稿输出不是垃圾**：0.6B 对同一 prompt 输出连贯中文（"MoE 是一种基于专家网络的架构…"，48 token 中 34 个不同），且与 target 前 2 个 token 一致（`[6050, 36]`）后分叉。
- **因此 α≈0 是真实的分布不匹配**：0.6B/1.7B 属 Qwen3 初代（思考型后训练），target 是 2507（非思考）；即使不看后训练，0.6B 与 30B 的首 token 分布也只在前 1–2 位重合。
- 与社区 40–60% 的数字冲突的原因：社区数字来自**同代同后训练**的 draft/target 对，且多在英文/chat-template 路径下测得。本项目是"初代小模型 → 2507 大模型"的跨代组合。

## 2. c 实测与**新发现：每步固定成本主导**

draft 步时（eager，贪心，prompt 512，3 次重复中位；单位 ms）：

| draft | TP | b1 | b8 | b32 |
|---|---:|---:|---:|---:|
| Qwen3-0.6B | 2 | **63.5** | 75.2 | 93.1 |
| Qwen3-1.7B | 2 | **63.8** | 72.9 | 96.9 |
| Qwen3-0.6B | 1 | **51.8** | 61.3 | 129.5 |
| Qwen3-1.7B | 1 | **52.4** | 62.7 | 135.0 |

target 单步（采用栈，P0 矩阵）：b1 **165.3 ms** → c(0.6B, TP2) = 0.384，c(1.7B, TP2) = 0.386。

**三条组内对比指向同一个结论：**

1. **模型大小几乎不影响步时**：0.6B 与 1.7B 都是 ~63.8 ms（差 0.5%）。若是权重带宽 bound，1.7B 应慢 2.5–3×。
2. **TP1 只比 TP2 快 ~12 ms**（52 vs 63.5）：all-reduce 不是主因（28 层 ×2 次 ≈ 12 ms，与实测差吻合）。
3. **0.6B eager b1 的 63.2 ms 里 forward 占 62.1 ms（98.2%）**，prepare 0.22 ms、sample 0.86 ms（`tests/p6_step_overhead.py` 分解，`/root/p7_step_overhead_06.json`）。

→ **每层约 1.4–2.2 ms 的固定开销**（0.6B 28 层 ≈ 40 ms 净 GPU 时间；8B 32 层 ≈ 74 ms，P6b 数据）。0.6B 单步的权重带宽下限只有 ~3 ms，所以 **约 90% 是每层固定成本**。

**这对 P7 是结构性的**：投机解码要 draft 跑 k+1 步，而每步都付这份固定成本；k=3 时 draft 侧就是 ~150–190 ms，与一次 verify（165 ms）同量级，无论 α 多高都不划算。所以即使换成 EAGLE3 头（α 0.8），只要 step 成本不变，最好也只有 ~1.1×。

## 3. 为什么这不是"再调一下就行"

对照 survey §7.1 的判决表，要过 1.3× 需要 (α, c) 落在表内加粗区。实测 (0.006, 0.39) 距最近的门槛（α=0.45, c=0.08）在两个维度上都很远：
- α 需要提升 **80 倍**（0.006 → 0.45）——只能靠训练过的草稿头（EAGLE3/PARD），且必须与 2507 同后训练；
- c 需要降到 1/5（0.39 → 0.08）——只能靠砍掉每步固定成本，这正好是图捕获（I1，当前 0/5）或逐层开销优化才能做到的。

两者都成立才可能过门，任一个不成立都无解。

## 4. 结论与去向

1. **S1 关闭为 no-go**，`docs/P7-implementation-plan.md` 的 M1–M4 **不启动**；EAGLE3/PARD（S6）从"远期可选"上调为**唯一可能路线**，且前置条件是先解决每步固定成本。
2. **新问题（记入 ISSUES）**：**每步固定成本 ~1.4–2.2 ms/层**，它同时压着
   - 单流延迟（30B b1 = 165 ms，其中固定成本占比待逐层拆分）；
   - 容量（0.94 req/s 硬饱和可能与每步固定成本有关）；
   - 以及所有"多步"方案（投机解码、图）。
   优先级**高于**投机解码，因为它的收益面更大且不依赖外部决策。
3. **下一步最便宜的两个测量**（各 ≤15 min）：
   - 30B 的同一套 step_overhead 分解（看 165 ms 里 forward/prepare/sample 与每层占比）——直接给出"砍固定成本能拿多少"的上界；
   - 0.6B 上逐层计时（28 层 × 每层前向），区分"launch 数量"与"单 kernel 慢"。若确认是 launch-bound，则 I1 图的 1.55×（0.6B b1 观测：graph 40.0 ms vs eager 63.2 ms）就是可直接兑现的收益，图从"低优"变"高优"。

## 6. 过程中的坑（供下轮省时间）

1. **一次一个模型**：同进程连开 0.6B → 1.7B 会因第一个模型的 18.85 GiB KV 未释放而断言 `no KV cache memory`（`used=24.21 > 24.0` 预算），随后 rank1 卡在 barrier（I12 的现场）。
2. **spawn 脚本必须有 `if __name__ == "__main__"`**：否则 spawn 子进程重跑模块级代码 → 递归 spawn + 挂死（本轮踩了一次，白等 ~10 分钟）。
3. 0a 早期版本只在末尾写 JSON，崩了就没产物 → 已改为逐条流式写 JSONL。
