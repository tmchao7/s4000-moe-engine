## ⚠️ 口径发现(必须与门结论一起读)

**跨 repeat 的 prompt 是确定性重建的**(`build_prompt` unique 模式 = `prompt_word-seed-request_id-position`,`benchmark_online.py:180-195`),因此 **rep2/3 的每个 prompt 都命中引擎 256-token 块粒度前缀缓存**,1k prefill 退化为"缓存续写"——rep1=冷缓存真实容量,rep2/3=暖缓存路径。三 repeat 中位数(冻结门的度量对象)实际度量的是**暖缓存路径**。I8 历史(P6d)每档只跑一次,无此效应;其 0% SLO 与本次 rep1 一致。

## 判定

1. **I8 的塌方机理定案**:冷缓存 1k 塌方是 **chunk 粒度问题**——chunk-1024 把冷 TTFT p50 砍 −56~57%(3.30/4.14/5.07 → 1.449/1.784/2.201),0.5 档冷态即过 ≤2 s 门(90.6%);1.0 档冷态仍塌(2.2 s)。**准入修复(I26)管的是稳定性**(零 429、无雪崩、全程无失败),**chunk 加大管的才是 TTFT 本身**——两者互补,缺一不可。
2. **按冻结门:chunk-256 与 chunk-1024 的三 repeat 中位 TTFT p50 全部 ≤2 s → 门 PASS**;但中位由暖缓存主导,**"1k 可服务"的准确表述是:①暖缓存(重复/模板化 prompt)任意 chunk 都 100% SLO;②冷缓存(真 unique)必须 chunk ≥1024 才在 ≤0.87 qps 的 0.5/0.75 档可用,1.0 档冷态仍需更大 chunk 或更低载**。
3. **推荐配置更新:1k 长上下文场景 chunk=1024**(P9 曾推荐 2048;1024 冷 TTFT 1.449 s 已过门且对短 prompt 的 TPOT 代价更小——本夜短 prompt 矩阵 chunk 恒 256 未受影响)。**生产默认 chunk-256 不动**(P10 冻结门仍然有效,其 TPOT +5~9.5% 的否决针对的就是短 prompt 场景)。
4. I8 条目可更新为"已闭合(机理+解法)":塌=chunk 粒度×冷缓存;解=chunk-1024(冷)/前缀缓存(暖)/准入(稳定)。
