# P8 — I19 每步固定成本:融合与 host-sync 的 A/B 判决(P1)

> 日期:2026-10-28。schema_version 1(证据 JSON);冻结门见 `docs/NIGHTLY-LOG.md` P1.1/P1.3。
> 栈:Qwen3-0.6B TP1 eager sdpa b1/b32,fcfs,max_num_seqs=1(b1)/32(b32);交错 A/B,同进程运行时切换。

## 0. 一句话结论

**I19 的"launch-bound → 融合换步时"因果链被本轮实测否定**:fused RMSNorm 把每步 launch 从 2,402 砍到 1,442(−960)、kernel device 时间从 31.9 砍到 21.1 ms(−33%),**decode 步时只降 0.76%**;MoE bmm 容量收缩把 bmm 行数砍 ~10×(S 256→25),**步时不动**。步时由一个既非 device 工作量、也非 launch 提交、也非 host-sync 的 ~20–30 ms/步固定等待决定;图 replay 是判决该等待的唯一实验,但被 30B TP2 wedge 阻断(I29)。

## 1. fused RMSNorm A/B(P1.1)

| 门 | 结果 | 数字 |
|---|---|---|
| G1 kernel L1(fp32 max_abs) | PASS | 6 组形状全部 **0.0**(probe 内 bitwise) |
| G2 端到端翻转率 | FAIL | 228 可比步 1 翻转,margin 1.375(≥0.5) |
| G3 自确定 | PASS | 两模式各 3 次全一致 |
| G4 性能(−≥8%) | **FAIL** | baseline 54.83 ms → fused 54.41 ms(**−0.76%**);CV 0.34%/0.23% |
| G5 launch 证据 | PASS | launch 2,402→1,442(−960);device 31.87→21.14 ms |

- G1/G2 矛盾的机理(逐模块诊断):真实路径 128 行时 eager `mean` 的归约切分与 Triton 不同 → 每层 0–1 元素差 1 bf16 ulp(probe 的 37/64/17 行恰好一致);1-ulp 差异经 28 层放大到 logits ~0.2–0.6,偶发近平局翻转。kernel 本身数值健康(L1 4.9e-4 ≪ 2e-3)。
- **判定:不采用(默认关,`NANOVLLM_FUSED_RMSNORM=1` 可开);代码与 A/B 保留为资产。**

## 2. host-sync 移除(P1.3)

- 实现:sampler 2 次 `bool()` → host 侧 `all_greedy`;prefill 96 次 `.tolist()` → prepare 时传 host list(`NANOVLLM_HOST_SYNC_FIX`,默认开)。
- T1 token 全等:PASS(b1 32 步、b32-greedy 16 步,配对 prompt)。
- T3 prefill-512 步时:**62.8→55.5 ms(−11.6%)**,run2 62.3→58.9(−5.4%),交错区间干净分离 —— **采纳(默认开)**。
- T2 b32-mixed sample 段:1.75→1.51 ms(−13.5%,0.5× 门是 30B 口径,0.6B 不可判)。
- 30B 复核(L2 内):512-token prefill 步时 424.9→409.6 ms(**−3.6%**,未达 −5% 门;方向与 0.6B 一致,幅度随模型变大摊薄)。
- T4 decode 步时:b1 −0.4%、b32-greedy −0.2% —— 再次确认 decode 对 host-sync 不敏感。

## 3. 对 I19 的更新认识

1. "2,401 launches × 13.5 µs" 的旧读法有误:13.5 µs 是 **device 时间均摊**(31.9 ms/2,401),不是 host 提交成本。
2. launch 数(−40%)与 device 时间(−33%)同时下降而步时不动 → **步时的关键路径不在 kernel 执行也不在提交**;0.6B 每步 ~20 ms、30B 每步 ~50–100 ms 量级的未解释等待(候选:驱动/运行时每步固定开销、MCCL/allocator 行为、同步语义)。
3. 下一轮最有信息量的三个实验:①30B TP2 图 replay wedge 修复后做 eager vs graph(直接消掉全部每步 host 参与);②300 步连续 decode 的 per-step 时间分布(检查周期性停顿,如 allocator/驱动);③torch.musa profiler 的 CPU 侧 timeline(看 host 在等什么)。
